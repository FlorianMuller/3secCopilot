Chapter 01 · Language

Swift, seen from JS, Go & a bit of C

You already think in types, functions and async. Swift mostly rearranges what you know and adds two ideas that pay off constantly in this project: optionals and value vs. reference types. This is the 20-minute orientation, not the manual.

What it is Syntax Optionals struct vs class Enums Protocols & closures Errors & async Memory (ARC)

1.1What Swift actually is

Swift is Apple's compiled, statically-typed language — the modern replacement for Objective-C. Mentally file it next to Go: compiled to a native binary, strong static types, garbage-pressure kept low, first-class concurrency. The flavour is closer to TypeScript + Rust: heavy type inference so it reads like a scripting language, but with strict null-safety and value semantics underneath.

Compiled
Ahead-of-time to a native ARM binary by the Swift compiler (via LLVM). No interpreter, no JIT. Same family as Go/C++.
Static + inferred
Every type is known at compile time, but you rarely write them out — like TS with strict on.
Memory
No GC. Uses ARC (automatic reference counting) — deterministic, like C++ smart pointers. See §1.8.
Null safety
There is no implicit null. A value that can be absent is a distinct type: an Optional. This is the biggest day-to-day difference.

1.2The syntax in one screen

Almost everything here has a direct JS/Go analogue. Read the comments — they map each line to something you already know.

Swift essentials
let title = "2026"        // const — immutable, type inferred as String
var count = 0            // let (mutable in JS sense)
let fps: Int = 30        // explicit type annotation, when you want it

// Functions: `func`, params are `name: Type`, return after `->`
func bitrate(for height: Int, fps: Int) -> Int {
  return height >= 1080 ? 16_000_000 : 8_000_000
}                          // note: 16_000_000 — underscores are just digit separators

// String interpolation with \( ), like `${ }`
let msg = "Encoding \(count) clips at \(fps)fps"

// Collections
let ids: [String] = ["A1", "B2"]     // array
let sizes: [String: Int] = ["720p": 8]  // dictionary (object/map)
for id in ids { print(id) }               // for…of
let doubled = ids.map { $0.uppercased() } // $0 = first arg shorthand
◇ For the JS/Go dev

let = const, var = a reassignable binding. The one that trips people: Swift's let/var is about mutability, not scope — there's no var-hoisting weirdness. Semicolons are optional and nobody uses them.

1.3Optionals — the one to internalise

An Int can never be nil. If a value might be absent, its type is Int? (an Optional) — a genuinely different type that the compiler forces you to unwrap before use. This is TypeScript's number | null with strictNullChecks, but enforced everywhere with dedicated syntax.

Working with optionals
var endMs: Double? = nil       // might hold a Double, might be nil

// 1. if-let: unwrap into a non-optional binding for the block
if let end = endMs {
  print("trim to \(end)")     // `end` is a plain Double here
}

// 2. guard-let: unwrap or bail out early (very common in this codebase)
func use(_ endMs: Double?) {
  guard let end = endMs else { return }   // no value → leave now
  // `end` stays unwrapped for the *rest* of the function
}

// 3. ?? — nil-coalescing (identical to JS ??)
let duration = endMs ?? 3000

// 4. optional chaining — like JS ?.
let w = settings.overlay?.cardFontSize
◇ You already met this in the module

In ExpoMontageModule.swift, every trim field is Double? — startMs/endMs are nil when the clip uses its full length. And guard let assetId = record.assetId, !assetId.isEmpty else { throw … } is exactly pattern #2: unwrap-or-fail at the top of the initializer.

1.4struct vs class — value vs reference

This distinction doesn't exist in JS (everything non-primitive is a reference) and is looser in Go. In Swift it's load-bearing:

struct
Value type. Copied on assignment/pass, like a Go struct or a C struct. No shared identity. Swift's default choice — most of your data models are structs.
class
Reference type. Passed by pointer, has identity, is ref-counted by ARC. Use when you need shared mutable state or a lifecycle — e.g. the long-lived MontageExporter.
The two, side by side
struct WriterConfig {        // value: copied when passed around
  let width: Int
  let height: Int
}

final class MontageExporter {   // reference: one instance, shared, mutated
  let taskId: String
  private var cancelRequested = false  // mutable lifecycle state
}
▸ Why it matters here

final class (the final just means "no subclassing", a small speed win) is used for the exporter and encode session because they own mutable state and must be a single shared thing that a cancel button can reach. Config/records are structs because they're just immutable bundles of numbers.

1.5Enums that carry data

Swift enums are far more powerful than C's integer enums or a TS string union — each case can carry its own associated values. This is a tagged union / sum type (like a Rust enum or a TS discriminated union), and your module leans on it hard.

MontageSupport.swift — the real thing
enum ExportClipSpec {
  case video(assetId: String, startMs: Double?, endMs: Double?, overlay: ClipOverlayContent?)
  case missingDay(durationMs: Double, overlay: ClipOverlayContent?)
  case card(durationMs: Double, lines: [String])
}

// You consume it with `switch`, which the compiler forces to be exhaustive:
switch spec {
case .video(let assetId, let start, let end, _):
  // handle a real clip; `_` ignores the overlay
case .missingDay(let durationMs, _):
  // draw a black beat
case .card(let durationMs, let lines):
  // draw the title card
}
◇ Mental model

It's the TS MontageClip union from ExpoMontage.types.ts — { type: "video" } | { type: "missingDay" } | { type: "card" } — but the compiler guarantees you handled every case and gives you the payload already unwrapped. The native ExportClipSpec is literally the Swift twin of that TS type.

1.6Protocols & closures

Protocols are interfaces (Go interfaces / TS interfaces) — a set of requirements a type can conform to. You'll see Record, Sendable, Error used as protocols in the module. Closures are anonymous functions / lambdas — the trailing-closure syntax { … } after a call is pure Swift sugar.

Closures & protocol conformance
// A closure stored as a property — the module's progress callback:
let sendProgress: (String, Double) -> Void   // takes (phase, progress)

// "trailing closure": the { } is the last argument, pulled outside the parens
let upper = ids.map { $0.uppercased() }

// conforming to a protocol — `: Record` means "this struct is a Record"
struct SpikeOptions: Record {
  @Field var width: Double = 1920
}

That @Field is a property wrapper — an annotation the Expo Modules API reads to marshal JS values into the struct. More on that in Chapter 02.

1.7Errors & async/await

Two pieces of very familiar machinery, with slightly different spelling:

  • Errors are thrown and caught, but a function that can throw must declare it with throws, and every call to it must be marked try. So the danger is visible at the call site — closer to Go's explicit if err != nil than JS's invisible throws.
  • async/await is nearly identical to JS. await suspends; the surrounding function is marked async. AVFoundation's modern API is async, which is why the module is full of try await asset.load(.duration).
throws / try / async — from buildComposition
func buildComposition() async throws -> AVMutableComposition {
  let asset = try await resolver.resolve(assetId: id)  // may throw, is async
  let duration = try await asset.load(.duration)
  guard let track = try await asset.loadTracks(withMediaType: .video).first
  else { throw MontageError.noVideoTrack(id) }  // throw a typed error
  return composition
}
▸ Project convention

Your CLAUDE.md says: in helper/reusable functions, don't catch errors — let the caller handle them. That's why the composition helpers freely throw and only the top-level exporter decides what to do (retry, degrade to a black beat, or emit onExportError).

1.8Memory: ARC, strong & weak

No garbage collector. Instead, every class instance carries a reference count; when the last reference goes away, it's freed immediately (deterministic, like C++ shared_ptr). Two reference flavours matter:

strong (default)
Keeps the object alive. Owning references.
weak
Does not keep it alive; becomes nil when the object dies. Used to break retain cycles and for back-pointers.
⚠ The bug you already hit

Phase 3's nastiest native bug (spec §0): AVAssetTrack.asset is a weak back-pointer. The code resolved AVAssets, inserted their tracks, then let the assets go out of scope — ARC freed them, the weak pointer went nil, and startReading failed with -11800. The fix — ChunkBuild.retainedAssets holding strong refs until the encode ends — is this section in practice. Same reason ClickSource.asset keeps an explicit strong ref with a comment about it.

The other memory concept in the module is autoreleasepool (spec §11.5): the encode loop makes hundreds of ~8 MB frame buffers per callback; draining them each iteration keeps peak memory flat instead of OOM-killing the app.

Chapter 02 · Architecture

How Swift plugs into React Native & Expo

Your app is JavaScript running in a JS engine. AVFoundation is Swift running on the device. The Expo Modules API is the wire between them — it turns a Swift class into something you can import and await from TypeScript. This chapter is that wire, end to end.

Why native The two worlds The Module DSL Data marshalling Events & promises Wiring & build

2.1Why drop to native at all

React Native lets you write UI in JS, but JS can't touch the phone's video hardware. Anything that needs AVFoundation / VideoToolbox — decoding footage, compositing frames on the GPU, hardware H.264 encoding — has to run in Swift. A native module is a small Swift package that exposes a few functions to JS; your UI stays in React, and the heavy lifting happens in modules/expo-montage/.

Spec §3 spells out why AVFoundation over ffmpeg: the whole decode → composite → encode pipeline stays on media hardware, several times faster and lighter than ffmpeg's CPU filter graph for a year-scale render.

2.2The two worlds, and the wire between

Picture two processes-of-the-mind in one app:

JS
Your React code
ExportScreen.tsx → src/services/montage.ts calls exportMontage(clips, settings). Pure TypeScript.
↕
The Expo Modules bridge
Serialises the JS arguments, hops threads, invokes the matching Swift function, and marshals the result back as a resolved Promise. You never write this layer — the API generates it.
SW
Your Swift module
ExpoMontageModule.swift receives typed Swift values and runs AVFoundation. Results and progress flow back the same wire.
◇ Closest analogy you know

It's like calling a WebAssembly export from JS, or a cgo function from Go: a foreign, faster runtime reached through a typed boundary that copies values across. The "old" React Native version of this wire was the bridge (JSON over an async queue); Expo's version uses JSI (direct C++ calls, much faster), but the mental model — marshal args → call → marshal result — is unchanged.

2.3The Module DSL — where JS names meet Swift

An Expo module is a Swift class with one method, definition(), that returns a little declarative description. This DSL (domain-specific language) is the entire contract with JS — each entry becomes a callable or an event on the JS side.

ExpoMontageModule.swift (trimmed)
public class ExpoMontageModule: Module {
  public func definition() -> ModuleDefinition {
    Name("ExpoMontage")                              // the JS-visible module name

    Events("onExportProgress", "onExportComplete", "onExportError")  // pushable events

    AsyncFunction("analyzeClips") { (assetIds: [String]) async -> [[String: Any]] in
      await ClipAnalyzer.analyze(assetIds: assetIds)  // ← runs Swift, returns to a JS Promise
    }

    AsyncFunction("exportMontage") { (clips: [MontageClipRecord], settings: MontageSettingsRecord) throws -> [String: Any] in
      // … starts the export, returns ["taskId": …] immediately
    }
  }
}
Name("…")
The string JS uses to find the module. Matches requireNativeModule("ExpoMontage") on the TS side.
AsyncFunction
A function whose Swift body returns a value (or throws) and surfaces in JS as a Promise. There's also Function for synchronous ones.
Events(…)
Declares named events the native side can push at any time — the basis for progress streaming (§2.5).

2.4Data marshalling: Records & the TS twin

JS passes plain objects; Swift wants typed structs. A Record is the adapter: a struct conforming to the Record protocol, whose @Field-annotated properties the API fills from the incoming JS object (with the defaults you give as fallbacks). You maintain the shape twice — once in TS for your own type-safety, once as a Record for the native boundary.

The same object, both sides
// TypeScript — ExpoMontage.types.ts
type MontageSettings = {
  renderSize: { width: number; height: number };
  fps: number;
  videoAverageBitrate: number;
  missingDayClick: boolean;
  mode: "preview" | "full";
  outputPath: string;
};

// Swift — ExpoMontageModule.swift
struct MontageSettingsRecord: Record {
  @Field var renderSize: RenderSizeRecord = RenderSizeRecord()
  @Field var fps: Double = 30
  @Field var videoAverageBitrate: Double = 16_000_000
  @Field var missingDayClick: Bool = false
  @Field var mode: String = "full"
  @Field var outputPath: String = ""
}
⚠ These two must stay in sync by hand

Nothing auto-generates one from the other. Add a field in TS, add the matching @Field in the Record, or the value silently falls back to its default on the native side. Note the type mapping too: JS number → Swift Double (then often cast to Int), JS boolean → Bool.

Going the other way — Swift back to JS — the module returns [String: Any] dictionaries (e.g. ["taskId": taskId]), which arrive in JS as plain objects. That's why return types are loosely typed on the Swift side but strongly typed in the TS declaration.

2.5Promises for results, events for progress

A long export can't be a single Promise that resolves 7 minutes later with no feedback. So the module uses both mechanisms, deliberately:

  • Promise — exportMontage returns immediately with a taskId, just acknowledging "started".
  • Events — progress, completion and errors stream over the declared events. Native calls self.sendEvent("onExportProgress", […]); JS listens with addListener.
Native push → JS listener
// Swift: fired repeatedly as the encode advances
self.sendEvent("onExportProgress", ["taskId": taskId, "progress": progress, "phase": phase])

// TypeScript: the shape is declared as an events map on the module
type ExpoMontageModuleEvents = {
  onExportProgress: (e: ExportProgressEvent) => void;
  onExportComplete: (e: ExportCompleteEvent) => void;
  onExportError:    (e: ExportErrorEvent) => void;
};

The [weak self] in those Swift callbacks (see ExpoMontageModule.swift) is §1.8 in action — the closure must not keep the module alive by itself, so it holds a weak reference.

2.6How JS finds the module, and how it builds

Three files stitch the Swift code into your app. This is the plumbing you rarely touch but should recognise:

expo-module.config.json
The manifest Expo autolinking reads at build time. Yours declares platform apple and module class ExpoMontageModule — that's how the native class gets discovered and compiled in without manual Xcode wiring. (This is the file open in your editor.)
ios/ExpoMontage.podspec
A CocoaPods spec — iOS's dependency/build descriptor. Lists the Swift sources and, here, the resource_bundles that ship click.caf into ExpoMontage.bundle. CocoaPods is roughly "npm for native iOS libs".
src/ExpoMontageModule.ts
The JS entry point: requireNativeModule("ExpoMontage") hands back the live native module, typed via a declare class so TS knows the signatures. Everything else imports from here.
src/ExpoMontageModule.ts — the JS handle
import { requireNativeModule } from "expo";

declare class ExpoMontageModule extends NativeModule<ExpoMontageModuleEvents> {
  analyzeClips(assetIds: string[]): Promise<ClipAnalysis[]>;
  exportMontage(clips: MontageClip[], settings: MontageSettings): Promise<{ taskId: string }>;
  cancelExport(taskId: string): Promise<void>;
}

export default requireNativeModule<ExpoMontageModule>("ExpoMontage");
▸ The build reality

Because this is a native module, it isn't hot-reloadable like JS — a Swift change needs a native rebuild. Your spec §0 notes the fast loop: edit in Xcode (make xcode-open-workspace, Cmd+R) or compile-check the pod target with xcodebuild … -target ExpoMontage without a device. JS changes still hot-reload through Metro as usual.

Chapter 03 · The module

How expo-montage turns metadata into one video

Given a list of clips (each with a trim range) plus settings, the module produces a single .mp4. Between those two points sits AVFoundation. This chapter gives you the vocabulary first, then the broad algorithm, then a map of which file does what.

Video vocabulary AVFoundation nouns The public API The broad algorithm Chunk & assemble File map

3.1Video terms, in plain words

You said you don't have the video vocabulary yet — here's the minimum to read the code and the spec's §4.2 table.

Resolution
Pixel dimensions of each frame, e.g. 1920×1080 ("1080p"). Bigger = sharper & heavier. The module's renderSize.
Frame rate (fps)
Frames shown per second — 30 or 60 here. Higher = smoother motion & more data.
Codec
The compression algorithm. H.264 (a.k.a. AVC) is the universal safe choice you're using — every phone, Photos, and YouTube read it. HEVC/H.265 is the newer, HDR-capable one (post-v1).
Profile
A feature tier within a codec. H.264 High = best quality/efficiency level for 1080p+ playback.
Bitrate
Bits used per second of video — the main quality/size dial. Spec §4.2 sets Premiere-class targets (16 Mbps @1080p30). File size ≈ bitrate × duration.
Container
The wrapper file format holding the encoded video + audio streams. .mp4 here.
Codec vs container
Container = the box (.mp4); codec = how the picture inside is compressed (H.264). Same box can hold different codecs.
Encode / decode
Encode = compress raw frames → H.264. Decode = the reverse. Both run on the phone's dedicated media chip (VideoToolbox), not the CPU.
SDR / HDR
Standard vs high dynamic range (brightness/colour). v1 outputs SDR BT.709 and tone-maps HDR sources down to it (spec §4.2).
B-frames
Compression frames that reference future frames. Great for size, but their reorder delay broke chunk concatenation — so the module disables them (AVVideoAllowFrameReorderingKey: false, spec §0).

3.2AVFoundation's nouns

These are the Apple types the module is built from. Learn these six and the code reads cleanly.

PHAsset
A photo/video as catalogued by the Photos library — an id + metadata, not the raw file. Your videoId is a PHAsset localIdentifier. Reached via the Photos framework.
AVAsset
The actual playable media (tracks, duration, transforms). You get one from a PHAsset via PHImageManager.requestAVAsset — which also downloads iCloud-offloaded footage on demand.
Track
One stream inside an asset — a video track, an audio track. Some clips (screen recordings) have no audio track → the module inserts silence.
AVMutableComposition
A virtual timeline you build by inserting time-ranges of source tracks. The spec's "exactly 2 tracks" (1 video + 1 audio) live here. Trimming is the insertion — nothing written to disk per clip.
AVMutableVideoComposition
The render recipe layered over the composition: output renderSize, frameDuration (fps), per-clip transforms (rotate/aspect-fit), and forced BT.709 colour.
AVAssetReader / Writer
The manual encode engine (spec §3): the Reader pulls decoded frames out of the composition, and the Writer compresses them to the file at your exact bitrate. Chosen over AVAssetExportSession precisely because it gives bitrate control.
CMTime
A rational time value (value/timescale) used everywhere instead of floats, so 1/30-second boundaries stay exact. Your trims are ms → converted to CMTime.

3.3The public surface

Everything JS can do, from src/ExpoMontageModule.ts:

analyzeClips(ids)
Metadata-only scan → [{ assetId, width, height, fps }]. Feeds the quality picker and the default render target (spec §4.1). No decode, no download; unresolvable assets are simply omitted.
exportMontage(clips, settings)
Starts the export, returns { taskId } at once. All real output arrives via events. Rejects if one is already running — one export at a time (it saturates the media hardware).
cancelExport(taskId)
Tears down reader/writer, deletes temp chunks & the partial output, then emits onExportError with message "cancelled".
events
onExportProgress { progress, phase }, onExportComplete { outputPath, durationMs, fileSizeBytes, peakMemoryMB, warnings }, onExportError { message, failedAssetId? }.
▸ Who calls this

Not your components directly. src/services/montage.ts is the JS service layer (spec §8) that reads videos_metadata, builds the day-by-day timeline, formats overlay strings with luxon in the device locale, computes the size estimate, then calls exportMontage and forwards events to ExportScreen.

3.4The broad algorithm

End to end, one export run:

1
JS builds the timeline
montage.ts turns the period into an ordered MontageClip[]: an opening card, then each day as a video (with trim + overlay) or a missingDay beat. Overlay text is pre-formatted here.
2
Native validates & sets up
ExpoMontageModule maps each record → ExportClipSpec, builds a WriterConfig (size/fps/bitrate) and OverlayStyle, and hands a new MontageExporter the whole plan.
3
Chunk the timeline
MontageExporter splits the ~365 items into ~monthly chunks of ≤31 items (chunkItemLimit) — bounded memory, since 365 open assets at once is an OOM risk (spec §5.2).
4
Encode each chunk
Per chunk: resolve its assets → build a 2-track composition → run an EncodeSession (Reader → CoreImage overlay/black-frame generation → Writer) to a uniform intermediate .mp4. Downloads & encode emit progress.
5
Assemble the chunks
One final pass over the chunk files: video passthrough (compressed samples copied, no re-encode) + one continuous AAC audio encode (avoids per-boundary clicks). Produces the single output file.
6
Report
onExportComplete fires with the path, duration, size and peak memory. JS offers Save / Share / Delete.

What happens inside one EncodeSession

This is the heart (spec §5.3). The Reader emits decoded frames; the loop decides per frame whether it needs an overlay:

Conceptual — the reader → writer pump
for each frame the reader emits {
  if this frame's time falls in an overlaid segment {
    frame = overlayCIImage.composited(over: frame)   // GPU CoreImage
  }
  if this is a black beat / card {
    frame = solid black + centered text straight into a pool buffer
  }
  writer.append(frame)                               // hardware H.264 encode
  drain autoreleasepool                              // keep peak memory flat (§11.5)
}
⚠ Why overlays aren't CATextLayers

The "obvious" way — AVVideoCompositionCoreAnimationTool with text layers — is rejected by AVAssetReader (it's export-session-only). So overlays are drawn once into a cached CIImage and composited between reader and writer. This is spec §5.3 and it's why MontageOverlay.swift exists.

3.5Why chunk-then-assemble (not one big pass)

Two problems force this shape:

  • Memory. A single composition holding 365 source assets exhausts memory. Chunking caps how many are open at once.
  • Audio seams. AAC encoders add "priming samples" at the start of each independently-encoded stream — naïvely concatenating chunks produces an audible click at every boundary (12 in a year). The fix: assemble video by passthrough (lossless copy) but re-encode all audio in one continuous pass, so there are no internal seams.
  • Bonus: chunk boundaries are natural resume points for a future background-export feature (spec §9.5).

The subtlety that cost a debugging session (spec §0): passthrough concat only works if the chunk streams have no B-frame reorder delay — hence B-frames are disabled, plus per-segment first-sample anchoring. You don't need this to use the module, but it explains the odd-looking encoder flags.

3.6File map

Where each responsibility lives under modules/expo-montage/ios/:

The boundary. The Module DSL, the JS-facing Records, and the one-export-at-a-time lock. Also holds the phase-1 SpikeComposer dev harness. (~339 lines)

Chapter 04 · Deep dive

Bitrate, resolution & file size

You spotted the key idea already: with no compression, a video's size is fixed by its pixels — there's no dial. The codec is what turns size into something you can choose, and bitrate is that dial. This chapter follows the numbers from raw pixels to the app's size estimate.

The raw number The dial appears Bitrate as budget Average vs constant File size = rate × time Rules of thumb

4.1The number nobody ships

A raw frame is just a grid of pixels, each pixel a fixed number of bits. So an uncompressed video's data rate is forced — resolution × colour-depth × fps, multiplied out. Nothing to choose. For 1080p30 at 24-bit colour (3 bytes/pixel):

Uncompressed 1080p30 — the forced rate
1920 × 1080        = 2,073,600 pixels per frame
× 3 bytes          ≈ 6.2 MB    per frame
× 30 frames/sec    ≈ 186 MB/s  ≈  1,500 Mbps   (1.5 Gbps!)

→ one minute ≈ 11 GB. A full year montage: ~200 GB. Unshippable.

That's why every video you've ever watched is compressed. The codec's whole job is to describe those same frames with drastically fewer bits, by discarding what the eye won't miss — redundancy within a frame (smooth areas) and between frames (a mostly-static background barely changes shot to shot).

~1,500Mbps
Raw 1080p30 data rate — fixed by the pixels
16Mbps
What the app actually encodes (spec §4.2)
~90×
Compression ratio — bits thrown away, invisibly
Uncompressed
~1,500 Mbps
H.264 High
16 Mbps

To scale. H.264 keeps roughly 1 bit for every 90 the raw frames would need — and you can't tell by looking. That sliver is the shipped file.

4.2Compression turns size into a dial

Here's the answer to your exact question: yes — bitrate is a parameter you hand the encoder, a target output data rate ("aim for ~16 million bits per second"). The same codec (H.264) can encode the same footage at 4 Mbps or 40 Mbps. It's the number in AVVideoAverageBitRateKey and every row of the spec's §4.2 table.

And yes — it is essentially "how much the video is compressed," read inversely:

Lower bitrate
Smaller file, more aggressive compression, more information discarded → visible artefacts creep in: blocking, smearing, banding in gradients.
Higher bitrate
Bigger file, less discarded, closer to the original — up to a point of diminishing returns where the eye can't tell any more (that's the "visually transparent" sweet spot Premiere aims for).
▸ Codec vs bitrate — don't conflate them

The codec (H.264) is the method of compression — the toolbox of tricks. The bitrate is the budget you allow that method to spend. Two separate choices: you could keep H.264 and halve the bitrate (smaller, worse), or keep the bitrate and switch to HEVC/H.265 (same size, better — because it's a smarter method). v1 fixes the codec at H.264 High and varies only the bitrate.

4.3Bitrate is a budget shared across pixels

This is the piece that makes the spec's table make sense. Bitrate and resolution are separate dials you set independently — but they interact, because a fixed bitrate is a fixed number of bits per second that all the pixels have to share.

Divide the shipped budget by the pixels it covers and you get bits-per-pixel — the real quality signal:

Same 16 Mbps, different resolutions
16 Mbps ÷ (1920×1080 × 30fps) ≈ 0.26 bits / pixel   1080p — plenty
16 Mbps ÷ (3840×2160 × 30fps) ≈ 0.06 bits / pixel   4K — starved, looks worse!

A 4K video at 16 Mbps looks worse than 1080p at 16 Mbps, because four times as many pixels are fighting over the same bits. So to hold the same quality, more pixels (higher resolution) or more frames (higher fps) each need a bigger budget. That's the entire logic of §4.2 — and why the app derives the bitrate from the chosen resolution/fps rather than letting you set it directly:

720p → 8 Mbps
Fewer pixels, smaller budget holds quality.
1080p → 16 Mbps
4× the pixels of 720p ⇒ ~2× the budget.
4K → 45 Mbps
4× the pixels of 1080p ⇒ big jump again.
…× 1.5 at 60 fps
Doubling fps only adds ~50% (not 100%) — see §4.5.

4.4"Average" bitrate — the VBR nuance

The key is AVVideoAverage​BitRateKey — note average. That signals VBR (variable bitrate): the encoder doesn't spend exactly 16 Mbps every second. It spends more on a complex, fast-moving shot and less on a simple, static one, averaging out to your target. The eye gets bits where it needs them.

CBR
Constant bitrate — same bits every second regardless of content. Simple, wasteful; used for live streaming where the pipe is fixed.
VBR (average)
What you're using. Allocates the budget intelligently across the timeline. This is what "Premiere-class high quality" means in spec §4 — a controlled VBR encode at a visually-transparent average, not a dumb constant rate.

Because it's an average, the real file lands close to the estimate but not to the byte — a montage of calm, static clips comes in a touch under; lots of motion, a touch over.

4.5File size = bitrate × duration

Once bitrate is the budget, file size falls out of one multiplication — this is literally the app's estimate (spec §4.2, §8.6):

The estimate formula
fileSize ≈ (videoBitrate + audioBitrate) × totalDuration ÷ 8

// bits/s × seconds = bits;  ÷8 = bytes.  Audio (AAC 256 kbps) is ~1.6% of the budget.

Note what's not in that formula: the number of clips, the resolution, the fps. They only affect size through the bitrate you pick. Bitrate and duration are the only two levers — which is why the app can update the estimate live as you toggle missing-day beats (duration) or change the resolution combo (bitrate).

4.6Rules of thumb to carry

  • Bitrate is the only lever on size. Resolution and fps move size only by moving the bitrate you choose.
  • Size is linear in both bitrate and duration. Double either → double the file. Independent of clip count.
  • ~4× the pixels ⇒ ~2× the bitrate to hold quality (720p→1080p→4K roughly doubles then jumps).
  • Doubling fps adds only ~50%, not 100% — consecutive frames are highly similar, so temporal compression gets most of the extra frames nearly free (that's why 30→60 goes 16→24, not 16→32).
  • Audio is a rounding error. 256 kbps AAC is ~1.6% of a 16 Mbps budget — you can almost ignore it in your head.
  • Below a threshold, lower bitrate stops saving grace and starts adding artefacts (blocking, banding). The §4.2 targets sit comfortably above that line — "visually transparent."
